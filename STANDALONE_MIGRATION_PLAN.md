# CircleFlow: план переноса в самостоятельное Windows-приложение

Дата проверки исходников: 2026-09-13.

Это самостоятельное задание для агента-исполнителя. Реализовать этапы последовательно, сохраняя существующие функции. Этот документ описывает будущую реализацию; код приложения в рамках подготовки плана не менялся, сборка и тесты не запускались. Проверен установленный SDK: 9.0.315.

## 1. Зафиксированные требования

- Название приложения: **CircleFlow**.
- Полностью убрать поддержку Flow Launcher. Не оставлять второй хост, совместимый плагин или слой совместимости.
- Сохранить существующий оверлей, поиск, OCR, перевод, распознавание музыки, результаты, анимации и поведение выделения.
- Оставить одну глобальную горячую клавишу открытия выделения. Значение по умолчанию: `Ctrl+Alt+Space`. Дополнительных горячих клавиш для музыки, OCR и перевода не будет.
- Добавить трей с четырьмя пунктами, строго в таком порядке: **Open**, **Settings**, **Support the project**, **Exit**.
- Support the project открывает `https://ko-fi.com/keekys` в системном браузере.
- Settings открывает пустое окно-плейсхолдер. Не переносить нынешнюю панель настроек и не реализовывать HTML-дизайн.
- Позже окно настроек будет реализовано на XAML. Уже сейчас хранение, проверку и применение настроек отделить от представления и оверлея.
- Не импортировать настройки и профили из Flow Launcher.
- Все управляемые приложением постоянные данные, настройки, логи и кэши хранить внутри одной папки CircleFlow, рядом с программой, в подпапке `Data`.
- Будущее место установки: `%LocalAppData%\Programs\CircleFlow`. Установщик в этот перенос не входит. Сейчас приложение работает из распакованной папки и не перемещает себя автоматически.

## 2. Принятые допущения и границы

Эти решения конкретизируют реализацию без новых вопросов к пользователю:

- Первый запуск EXE запускает приложение в трей без автоматического открытия оверлея или Settings.
- Open запускает выделение, когда сессия не активна; при активной сессии не отменяет ее и не создает вторую. Повторная горячая клавиша сохраняет текущее поведение: отменяет отменяемую сессию и игнорируется при Uploading.
- Повторный запуск EXE передает команду Open существующему экземпляру и завершает второй процесс. Один экземпляр на пользователя в интерактивной Windows-сессии, в том числе при запуске копий из разных папок. Данные принадлежат папке первого экземпляра.
- Закрытие Settings, оверлея или окна результатов не завершает приложение. Settings открывается в единственном экземпляре; повторное обращение восстанавливает и активирует его.
- Двойной щелчок по значку трея выполняет Open; правый щелчок открывает меню. Одиночный левый щелчок не запускает захват.
- Установщик, автообновления, автозапуск с Windows, подпись релиза и изменение UI-дизайна вне scope.
- Первый артефакт: ZIP с папкой приложения для win-x64, публикация self-contained, без single-file, trimming и Native AOT. Целевой framework пока сохраняется: `net9.0-windows10.0.19041.0`. Обновление .NET рассматривать отдельно.
- Системный WebView2 Runtime используется как и сейчас. Упаковка собственного Fixed Version Runtime и его установщик вне scope. Отсутствие Runtime должно давать понятную ошибку при обращении к зависимой функции, а не ломать старт трея и независимые функции.
- В репозитории фактически только `Languages/en.xaml`; первый релиз остается английским. Загрузчик допускает поиск ресурса для системной культуры и fallback к английскому без добавления новых переводов и переключателя языка.
- Не добавлять FileSystemWatcher и живую перезагрузку JSON. Ручное редактирование JSON поддерживать при выключенном приложении.
- Требование единой папки касается собственных записей приложения и явно задаваемых профилей WebView2. Оно не означает перенос системного WebView2 Runtime, OCR language packs, системных журналов Windows или данных внешнего браузера. Не обещать отсутствие любых системных временных файлов.
- HTML `design/app_fluent.html` не является заданием на реализацию; `design/` сейчас игнорируется Git. Не менять его и не добавлять в релиз.

Обязательных открытых вопросов к пользователю для этого объема нет. Допущения выше не расширять до реализации будущего дизайна или функций из макета.

## 4. Архитектурные ограничения

- Сохранить один основной проект и текущий namespace `CircleToSearch`; не делать массовое переименование всего проекта ради брендинга.
- Все соединения служб и фабрик задавать в `CTS/CompositionRoot.cs`. Точка входа только передает управление bootstrap-композиции.
- CompositionRoot создает объекты; решения о применении настроек и завершении работы вынести в профильные классы.
- Constructor injection и конкретные небольшие классы; интерфейсы добавлять только на реальных границах или для нужных тестов.
- Не вводить service locator, DI-контейнер, глобальный event bus, абстрактные базовые классы или общую платформу нескольких хостов.
- Framework-типы WPF допустимы; запрет на implementation inheritance не требует отказываться от стандартного механизма WPF-окон.
- Fixed UI colors брать из `CTS/Ui/PluginPalette.cs`; пользовательские строки из `Languages/en.xaml`. Не создавать второй источник палитры или строк.
- Обновить устаревший пункт AGENTS.md про тонкий Flow-адаптер на тонкую самостоятельную точку входа. Это следствие прямого требования удалить Flow, дополнительного разрешения не требует.

### Границы частей

- `AppPaths`: неизменяемые абсолютные пути, без зависимости от текущей рабочей папки.
- `SettingsStore`: загрузка/сохранение JSON и файловая целостность, без UI, HWND и RegisterHotKey.
- `SettingsService`: актуальные значения, проверка, последовательное применение и результаты ошибок. Сервис не знает об окнах.
- `TrayIcon`: значок и меню, переданные команды; не создает сервисы поиска и не пишет JSON.
- `SettingsWindowController`: создать/показать/скрыть единственное пустое окно, больше ничего.
- `AppLifetime`: единый путь остановки, блокировка повторного выхода, владение подписками оболочки.
- `SingleInstanceCoordinator`: mutex, локальный канал активации и доставка только команды Open, без arbitrary command execution.
- `AppRuntime`: владение функциональными ресурсами и Start/Open/Stop; не создает SettingsPanel и не возвращает Flow Result.
- Оверлей получает параметры своей сессии и узкие действия сохранения выбора/согласия. Он не получает окно настроек, DataContext или файловое хранилище.

Имена новых файлов рекомендательные, ответственность и направление зависимостей обязательны. `PluginRuntime` переименовать в AppRuntime и вынести из CompositionRoot в свой файл. Массовое переименование PluginLog/PluginPalette и всех тестов не является целью.

### Контракт настроек и будущего XAML

Переименовать PluginSettings в AppSettings с сохранением текущих JSON-полей и значений по умолчанию. Возвращать копии или immutable snapshots; исключить доступ к общему изменяемому объекту из UI/функций.

SettingsService должен предоставлять чтение snapshot и операции изменения с проверяемым результатом. Изменения провайдера и consent выполняются как patch к последнему состоянию под общей сериализацией, а не записью устаревшей полной копии. При ошибке сохранения актуальное состояние не меняется.

Общие редактируемые параметры применять через тот же сервис. Для изменения hotkey использовать отдельную операцию сервиса с внедренным действием регистрации: проверить синтаксис, попробовать применить, сохранить и commit; при ошибке сохранения вернуть прежнюю регистрацию. При неудаче регистрации сохранить прежнюю рабочую клавишу, насколько позволяет Windows, и явно отразить фактический статус. Не сообщать успех, если восстановление регистрации не удалось. Не сохранять это поведение в будущий code-behind окна.

Параметры конкретной сессии фиксируются один раз перед ее запуском: задержка скрытия, отступ, минимальное выделение, максимальная сторона изображения, OCR-язык, язык перевода. Передавать их через session options, расширяя существующие OverlayLaunchOptions/контекст фабрик. Убрать поздние чтения общего settings из crop-делегата в CompositionRoot и языковых делегатов OverlayControllerFactory. Передать MaxLongSidePx в операции VisualSearchWorkflow, включая PrepareTraceAsync. Не добавлять глобальное поле current session settings.

Выбор провайдера внутри активного оверлея и принятие/сброс согласия действуют сразу, как сейчас. Это не замораживать общим snapshot. Согласие считается принятым только после успешного сохранения. Провайдер активной сессии остается выбором ее UI, а сохраненный провайдер задает начальный выбор следующей сессии.

Будущий SettingsViewModel получит только SettingsService и необходимые каталоги вариантов (например, OCR-языки). В этом этапе не создавать полноценный ViewModel с неиспользуемыми полями, навигацией и командами будущего дизайна. Достаточно реализованного и проверенного независимого сервиса. Плейсхолдер не обязан иметь DataContext.

## 5. Единое размещение файлов

```text
CircleFlow/
  CircleFlow.exe
  CircleFlow.dll
  *.dll, *.deps.json, *.runtimeconfig.json, ...
  Languages/en.xaml
  Images/app.png
  Images/app.ico
  Extensions/uBlockOriginLite.zip
  LICENSE, THIRD_PARTY_NOTICES.txt, THIRD_PARTY_LICENSES/
  Data/
    settings.json
    settings.json.bak              # предыдущая корректная версия при записи
    Logs/
    Profiles/
      Search/                     # включая распакованное расширение и кэш
      ImageTranslation/
      TraceVideo/
    Temp/                         # собственные временные файлы, если появятся
```

- Корень вычислять из `AppContext.BaseDirectory`, не из cwd, реестра или Flow metadata. AppPaths принимает явный корень в тестах.
- Будущий установщик кладет именно эту структуру в `%LocalAppData%\Programs\CircleFlow`; в приложении этот путь не хардкодить.
- Все три вызова создания окружений WebView2 должны получать конкретный userDataFolder. Проверять фактический `CoreWebView2Environment.UserDataFolder`: среда/политика может переопределить путь. При обнаруженном размещении вне Data не продолжать молча использовать внешний профиль; сообщить ошибку зависимой функции, не удалять внешние данные.
- На первом старте проверить возможность создать и записать Data. Если папка недоступна, показать локализованную startup-ошибку с предлагаемым пользовательским расположением и завершиться. Не переключаться молча на Roaming, Temp или другую папку и не запрашивать elevation.
- JSON записывать во временный соседний файл внутри Data, закрывать запись, затем атомарно заменять основной файл. Backup тоже внутри Data. Сериализовать записи, не допускать потери параллельных изменений.
- Отсутствующий JSON: текущие defaults и создание файла. Поврежденный JSON: сохранить исходник как settings.corrupt-<timestamp>.json внутри Data, попытаться восстановить корректный backup, иначе defaults; показать одно уведомление. Если сохранить поврежденный исходник не удалось, не перезаписывать его, сообщить ошибку.
- Поля валидировать и нормализовать в одном месте: MaxLongSidePx 256..8000, PaddingPx 0..100, HideDelayMilliseconds 0..2000, LassoMinDiagonalPx 1..1000 (верхний предел является техническим допущением), корректный формат hotkey, известный provider id, непустые языковые теги проверять через существующие механизмы культуры/каталога. При загрузке непригодные значения заменять defaults и фиксировать диагностику; при программном Apply возвращать ошибку без частичного commit. Недоступный OCR-пакет сохраняет текущий fallback OcrLanguageCatalog.
- Не менять процессные TEMP/TMP и чужие каталоги ради требования одной папки. Собственные временные файлы направлять явно в Data/Temp.
- ZIP создавать из чистого publish-каталога до пользовательского запуска. Не включать Data, пользовательские профили, логи, настройки и персональные данные из smoke-тестов.
- Обновление файлов приложения в будущем должно сохранять Data. Никаких команд рекурсивной очистки каталога установленного приложения в текущем build script.

## 6. Этапы реализации

### Этап 1. Самостоятельный host и зависимости

Файлы: CircleFlow.csproj, Main.cs, CTS/CompositionRoot.cs, CTS/Trigger/QueryTrigger.cs, plugin.json, AGENTS.md; новые Program.cs и CTS/AppRuntime.cs.

1. Зафиксировать исходный git status и baseline build/test перед изменениями. Пользовательские изменения не перезаписывать.
2. Переключить OutputType на WinExe, AssemblyName на CircleFlow; сохранить namespace и путь csproj. Перенести нужные version/product metadata из plugin.json в свойства проекта, не терять версию 0.5.1 без отдельного решения о релизе.
3. Удалить Flow package, адаптер Main, QueryTrigger и plugin.json из исходников/доставки. Удалить Flow-зависимые сигнатуры runtime.
4. Удалить оба target, исключающие WinRT.Runtime.dll. Не переносить Flow-like AssemblyLoadContext в standalone-приложение.
5. Создать STA bootstrap и WPF Application с ShutdownMode.OnExplicitShutdown и без StartupUri. Сборку зависимостей оставить в CompositionRoot, lifecycle отдать AppLifetime. Сохранить ResourceRollbackScope для частично созданного runtime.
6. Добавить app manifest с asInvoker и подходящим PerMonitorV2 DPI awareness; сохранить текущую thread DPI-политику OverlaySessionFactory и проверить их совместную работу.
7. Обновить тесты/пути, которые ищут CircleToSearch.dll. Не тянуть старую DLL из bin после переименования.

Результат этапа: проект собирается как EXE без API Flow, имеет собственный WPF message loop. Финальный приемочный запуск без Flow выполняется после этапов 2-6.

### Этап 2. Пути, ресурсы и локализация

Файлы: новый CTS/AppPaths.cs, локальный источник строк в CTS/Ui, CompositionRoot, PluginLog, TranslationMemoryProfiler, SearchBrowserHost, GoogleImageTranslationSigner, фабрика TraceVideoPreview.

1. Реализовать схему каталогов из раздела 5; создавать директории только после подтверждения, что процесс является основным экземпляром.
2. Разделить asset directory и writable data directory во всех параметрах. Архив расширения и иконки читаются из assets, расширение распаковывается в Search profile.
3. Загрузить строки en.xaml в read-only словарь до создания фоновых потоков. Для текущего формата строк можно использовать XDocument, как в TestUiStrings; не требуется загрузка WPF ResourceDictionary на фоновых потоках. Выдать существующему UiStrings делегат чтения.
4. Поиск культуры: exact culture, neutral culture, en; fallback по отсутствующему ключу к en. Не менять CurrentCulture форматирования и системный язык перевода только потому, что UI английский.
5. Добавить строки трея, заголовка Settings, ошибок startup/storage/hotkey/activation/shutdown. Сохранить существующие ключи функционального UI; не выполнять массовое переименование plugin_-ключей.

## 7. Проверки и команды

Все команды ниже выполняются из корня репозитория в PowerShell. Это команды для реализации, они не выполнялись при написании плана.

Baseline и финальная локальная регрессия:

```powershell
dotnet build .\CircleFlow.csproj -c Release
dotnet test .\tests\CircleToSearch.Tests\CircleToSearch.Tests.csproj -c Release --filter "Category!=Live"
```

После изменения lifecycle/settings сначала запускать соответствующие тесты, затем один полный non-Live прогон. Не повторять весь набор без новых изменений или выявленной проблемы. Существующие визуальные тесты с env gate не считать выполненными визуальными проверками, если gate не был включен.

Публикация после реализации:

```powershell
dotnet publish .\CircleFlow.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=false -p:PublishTrimmed=false -o .\bin\publish\CircleFlow
powershell -ExecutionPolicy Bypass -File .\build_release.ps1 -NoPause
```

Проверка прямых остатков Flow в production source (ожидается отсутствие совпадений, exit code rg 1 нормален):

```powershell
rg -n 'Flow\.Launcher|PluginInitContext|IAsyncPlugin|ISettingProvider|IPluginI18n|LoadSettingJsonStorage|SaveSettingJsonStorage|UseHostWinRtRuntime|RemoveStalePrivateWinRtRuntime' CTS CircleFlow.csproj Program.cs
```

Дополнительно поиск всех мест создания профилей/файлов для ручного аудита:

```powershell
rg -n 'CreateAsync\(|userDataFolder|UserDataFolder|File\.|Directory\.|GetTempPath|GetFolderPath' CTS
```

### Необходимые автоматические проверки

- SettingsStore: defaults; round-trip всех полей; поврежденный JSON и backup; недоступная папка/сбой записи; основной файл не становится обрезанным; не теряются одновременные patch провайдера и consent.
- SettingsService: ошибочный Apply не меняет состояние; consent только после сохранения; смена hotkey и откат при конфликте/ошибке диска; корректно сообщается неудавшийся rollback.
- Session options: изменение настроек после старта не меняет текущую обработку изображения и языки, но влияет на следующую сессию; provider и consent внутри текущего оверлея продолжают действовать.
- AppPaths: абсолютный корень не зависит от cwd; все собственные записываемые пути внутри Data; профиль не переходит на неявный default.
- Localization: все типизированные строки разрешаются; exact/neutral/en fallback; en.xaml и ресурсы доступны в publish, не только из исходников.
- Activation: Open не отменяет активную сессию, hotkey отменяет Cancelable; параллельные запросы не открывают два оверлея; остановленный runtime не принимает команды.
- Singleton: два одновременно запускаемых процесса дают один runtime; startup race, IPC timeout, прежний владелец завершился; второй процесс не пишет свои Data и не регистрирует hotkey.
- Lifetime: повторный Exit; выход во время старта/захвата/распознавания/перевода/открытия браузера; ошибки одного cleanup не пропускают остальные; watchdog не срабатывает на обычном выходе.
- WinRT: совместная инициализация OCR, обычного WebView2 и WebView2CompositionControl в standalone host; отсутствие duplicate ComWrappers failure. Проверять в том числе опубликованный процесс, поскольку test host может иначе разрешать сборки.
- Сохранить подходящие существующие SearchCoordinatorTests, ProviderSelectionStoreTests, OcrTranslationSettingsTests, PluginRuntimeLifetimeTests, OverlaySessionLifecycle/OwnershipTests, HotkeyWindowTests, SearchBrowserHostTests, PrivacyLoggingTests и прочие функциональные тесты.
- Не писать хрупкие тесты, зеркалящие порядок создания Grid/Border. Пустое окно и вид трея проверяются smoke-проверками.

### Ручная приемка из распакованного ZIP

1. Запуск без работающего Flow и, предпочтительно, на машине/VM без его установки. Нет консоли и стартового окна, есть один значок трея.
2. Четыре пункта в правильном порядке. Open запускает прежний оверлей; Settings показывает пустое окно; повторное Settings активирует тот же экземпляр; Close не завершает процесс.
3. Support открывает ровно заданную Ko-fi ссылку без автоматического действия пожертвования.
4. Ctrl+Alt+Space, Esc, повторный hotkey, повторный EXE и Open при активной сессии соответствуют разделу 2.
5. Пока открыто Settings или меню трея, Open не захватывает их в снимок. Проверить окно результатов на прежнее ожидаемое поведение.
6. Поиск Google Lens / Yandex / trace.moe, OCR и копирование, перевод с первым consent и его сбросом, музыка, открытие результатов и видео работают как до переноса. Внешние сбои провайдера отличать от регрессии хоста.
7. Закрыть и открыть приложение: выбранный провайдер и consent сохранены. В Data видны settings, logs и три профиля по мере использования; рядом с EXE не появляется непредусмотренный `.WebView2`-каталог.
8. Переместить выключенную распакованную папку в другой writable-путь с пробелами/кириллицей и запустить из иной cwd: данные и ресурсы остаются при приложении. Проверить запуск вручную из будущего `%LocalAppData%\Programs\CircleFlow` без установки и без прав администратора.
9. Недоступная для записи папка дает ошибку без скрытого fallback; отсутствующий WebView2 Runtime не ломает трей; конфликт hotkey не отключает Open.
10. Оверлей на разных мониторах с 100/125/150/200% DPI, отрицательными координатами и разными taskbar positions не смещается.
11. После перезапуска Explorer значок восстанавливается. Exit при активных операциях удаляет значок, завершает процесс, освобождает hotkey; новый экземпляр стартует без конфликтов.
12. Проверить содержимое ZIP: нет Flow DLL/plugin.json, Data, design, tests и личных профилей; есть собственные .NET/WinRT зависимости, native loader и необходимые assets/notices.

## 9. Проверенные технические справки

- [WPF ShutdownMode](https://learn.microsoft.com/en-us/dotnet/api/system.windows.application.shutdownmode): OnExplicitShutdown позволяет приложению жить после закрытия последнего окна.
- [WebView2 user data folders](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/user-data-folder): профиль содержит браузерные данные и кэш; custom path требует прав записи, фактический путь доступен через UserDataFolder.
- [Single-file deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview): single-file может использовать извлечение вложенных компонентов. В этом плане выбран обычный каталог self-contained publish, чтобы не добавлять такую схему размещения.
